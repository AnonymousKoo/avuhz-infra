## Explicit authority boundary

`LocalTestInfrastructureExecution` is constructed exclusively by a trusted TEST
harness. It independently provisions original PR761 trust records, PR762 policy
and human records, a separate immutable `ExecutionApproval`, independent initial
`SimulatedState`, and an explicit SQLite file under `/tmp`. Never derive these
records from a requester. The harness gives requesters only the bound `execute`
method and selected principal/execution handles. It retains construction, source
access, file access and handle distribution privileges.

`ExecutionApproval` explicitly registers `APPLY_FICTIONAL_STATE`, execution ID and
version, ACTIVE/REVOKED status, and the exact existing diagnostic approval record.
That nested immutable record pins the human and approval IDs/version, full scope,
manifest ID/digest/version, desired and expected-current digest/version, original
observation and source digest, policy ID/version/decision digest, request/challenge,
fixed `fictional.executor01`, time bounds, one attempt and zero recoveries.
Registration is a separate affirmative fixture, not generated by a successful
comparison. The human's existing REVIEW capability alone grants no mutation.
There is no real human role assertion or human authorization attestation here.

Each instance mints a new built-in object handle for its explicit execution
approval. Exact type and object identity are required. Diagnostic records,
results, strings, equality traps and handles from another instance are rejected.
The request remains the unchanged closed PR760 comparison request. It cannot
choose an operation, executor, SQL, path, clock, policy, failure flag or approval
registration. The harness binds the comparison and human/diagnostic handles.

Every invocation recomputes the original trust, policy and human approval review
for the exact request. Only `APPROVAL_MATCH_DIAGNOSTIC` with authority effect
`NONE` can proceed to the separate explicit execution approval check. Comparison
never becomes execution permission. Results expose bounded codes only and retain
`authority_effect=NONE`. Gate 5 records an attempt only. A confirmed CAS and
received acknowledgment return/persist ATTEMPTED, acknowledged but unverified.
Gate 6 requires an independent poststate verifier/attestation in the next milestone;
the executor cannot certify itself or return VERIFIED.

## SQLite durability model

The constructor initializes `simulated_resource_state` from an independent
harness fixture only when creating the registry schema. Reopening never resets
state or fills a missing state row. The full seven-field scope is stored as a
canonical JSON key, including principal, tenant, environment, namespace, class,
resource and owner. All observation and CAS predicates use that exact key.
The pre-state observer uses a separate `mode=ro` SQLite connection. It is never
used for poststate certification.

`execution_registry` durably binds execution and diagnostic approval IDs/versions,
request, challenge, full scope and a domain-separated SHA-256 digest of the entire
explicit approval. Revocation is sticky. Conflicting registrations cannot replace
records. Unique execution ID, approval ID, request and challenge prohibit reuse
across versions; the digest is separately unique. The immutable per-instance
registry models one explicit approval; independent instances share the ledger.

`local_attempts` stores the same identity/scope/digest bindings and only
ATTEMPTED or UNCERTAIN evidence, enforced by a SQLite CHECK. Reservation uses `BEGIN IMMEDIATE`,
checks durable revocation and consumption, scopes prior results before returning
them, freshly observes the on-disk prestate and compares its digest/version with
the registered expectation. Inserting the attempt and consuming the approval
commit atomically before any fake dispatch. Unique keys plus SQLite writer
serialization work across threads and processes. SQLite's bounded five-second
lock wait is contention handling, not an execution retry.

The fixed fictional executor opens a separate transaction, rechecks durable
revocation, then conditionally updates the one scoped state row from exactly the
expected digest/version to exactly the pinned desired digest/version. It accepts
no arbitrary SQL or executor callback. A concurrent state change makes the CAS
fail. After the effect commits, confirmed CAS and received acknowledgment permit
only ATTEMPTED in the outcome transaction. No poststate observation is performed
by the executor, and no independent verification is implemented here.

There is no dispatch retry, recovery, compensating effect or automatic reconciliation.
A repeated exact invocation returns its scoped recorded outcome without dispatch,
or fails closed if current policy/authority is no longer valid. A crash after
reservation leaves ATTEMPTED. Lost acknowledgment, effect failure, failed
CAS or write uncertainty cannot produce VERIFIED. Outcome persistence failure
returns UNCERTAIN and leaves ATTEMPTED on disk. Restart never upgrades that row
merely because the desired state happens to be present. Reservation refusal emits
a bounded failure code and performs no effect; ambiguous reservation commits
remain protected by the durable attempt on a subsequent invocation.

ATTEMPTED is also the durable reservation marker: after an interrupted or uncertain
post-reservation window it does not prove acknowledgment or even an effect. Replays
return that stable ambiguity without redispatch. Unknown or legacy VERIFIED rows
return UNCERTAIN without upgrading, rewriting or dispatching. Use fresh test DBs
for this source contract; old-schema test DBs cannot be reused across contract
changes. No schema evolution or existing-data reset is implemented or authorized.

Harness-owned immutable `TestFailures` flags model reservation refusal, crash
after reservation, intervening state change, effect write failure, lost ack,
and outcome write failure. These flags cannot be injected through `execute`.
The former `verification_unavailable` flag is retired. Tests also use actual SQLite refusal triggers, an independent
effect audit trigger, and joined foreground thread/process workers. No external
service or background worker is started.

## Limits and review

SQLite models local durability under a trusted filesystem and database engine;
it is not provider attestation, authenticated ownership, RLS, cryptographic
human approval, a live revocation feed or exactly-once infrastructure execution.
The fixed harness clock supplies source windows, not elapsed wall-clock proof.
New harness instances can register durable revocation; immutable policy/human
snapshots must be freshly provisioned by the harness. Revocation is serialized
with the effect transaction and cannot retroactively undo a committed effect.
Filesystem tampering, deleted/replaced databases, reflection, monkeypatching,
stolen handles and hostile Python execution are outside this in-process model.
Test IDs and digests are fictional, and no real PII or credentials are retained.

The sole-engineer security self-review checks authority separation, exact types,
full-scope reads and writes, SQL parameter binding, durable consumption, CAS,
revocation, sanitized exceptions and uncertain outcomes. This is not an
independent review or full v1 certification. Security and Infrastructure modeling
advance; live Automation and first-client Business readiness do not change.
